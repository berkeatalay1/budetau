Personal Budget Planner — Feature List & Roadmap

A complete, status-tagged catalogue of features for the local-first budget planner (Tauri v2 + Vue 3 + SQLite). Phase 1 (Local Infrastructure) is delivered; Phases 2 and 3 plus two cross-cutting tracks are planned. Items the team chose not to pursue yet are recorded in the Deferred Backlog so nothing is lost.

Phase 1 — Local Infrastructure DONE

The foundation: a building, testable desktop app with a privacy-first local database and a typed bridge between Rust and Vue. All work is verified (11 Rust tests, clippy + ESLint clean, frontend type-checks).

FeatureWhat it delivers
Desktop shell ✓Tauri v2 + Vue 3 + TypeScript + Vite. Strict tsconfig, ESLint (flat) + Prettier, clippy + rustfmt.
SQLite schema ✓5 tables (app_profiles, accounts, categories, budgets, transactions); money as INTEGER cents; user_version-gated migrations.
Cloud-sync safety ✓PRAGMA journal_mode = DELETE disables WAL so no -wal/-shm sidecar files corrupt under iCloud/Dropbox. Path resolves to Documents, falls back to app-data.
Atomic balances ✓Inserting a transaction updates account balance(s) inside one DB transaction — expense/income/transfer, with rollback on invalid transfer. Balances can never drift.
Typed IPC bridge ✓9 #[tauri::command]s returning Result<T, String>; api.ts typed wrappers via @tauri-apps/api/core; serde camelCase mapping.
Frontend foundation ✓Pinia stores (account/transaction/budget), Vue Router (dashboard/transactions/settings), Tailwind palette, responsive sidebar shell. Settings shows the live DB path.

Phase 2 — Budgeting & Core UX PLANNED

Turns the data layer into the product. This is where the app becomes usable day-to-day: a live dashboard, fast entry, full transaction management, and the budget alerts that are the spec's headline.

1. Dashboard Rendering

  • Hero summary: Total Spend vs Total Income for the current month, with net delta.
  • Budget cards: responsive grid, one card per active category, each with a spent-vs-remaining progress bar and the category color.
  • Empty & loading states for first-run users with no data yet.

Backend: new aggregation commands get_month_summary and get_budget_progress (SUM over transactions grouped by category, joined to budgets). Frontend: DashboardView.vue + BudgetCard.vue.

2. Budget Alert Banners

  • Threshold detection: banners when a category is near (default ≥ 90%) or over its limit — e.g. "Dining Out is at 95% of budget".
  • Severity styling: distinct "warning" (near) vs "over budget" treatments.
  • Configurable threshold per budget.

Schema: add budgets.alert_threshold (REAL, default 0.9). Computed from the same progress aggregation as the cards — no double counting.

3. Rapid Entry Modal

  • Trigger: floating action button (FAB) + global Cmd/Ctrl+K shortcut.
  • Streamlined default: three fields — Amount, Category (autocomplete from categories), Date (defaults to today).
  • "Add Details" expansion: optional Note, Account selector, type (expense/income/transfer) and transfer destination.
  • Optimistic update: store reflects the new transaction immediately, reconciles on command return.

Frontend: QuickAddModal.vue, global keybind handler. Reuses the existing create_transaction command.

4. Transaction Management — Edit / Delete + Search / Filter

  • Edit & delete complete the CRUD (currently create/list only), each with atomic balance reversal: reverse the old transaction's effect and apply the new one in a single DB transaction.
  • Card-based list: TransactionCard.vue showing category color/icon, amount, and date — clean cards, not a dense grid.
  • Search across note/category and filters by date range, account, category, and type.

Backend: update_transaction, delete_transaction (balance-safe). Schema: indexes on transactions(date), (account_id), (category_id) for fast filtering.

Phase 3 — Automated Ingestion & Analytics PLANNED

Scales the app from manual entry to real-world volume and insight.

5. CSV Bank Import

  • Local-only parsing via a Rust CSV parser (the csv crate) — statements never leave the machine.
  • Column mapping UI: map arbitrary bank columns to date/amount/note/type.
  • Preview & confirm: review parsed rows before they commit; whole batch inserts atomically with balance updates.
  • Dedupe: per-row import hash prevents re-importing the same statement twice.

Schema: new import_batches audit table + transactions.import_hash (nullable, indexed). Backend: preview_csv_import, commit_csv_import.

6. Charts & Trends

  • Cash-flow over time (line) — income vs expense by month.
  • Category breakdown (pie/donut) for a selected period.
  • Month-over-month comparison (bar).

Backend: read-only aggregation commands or SQL views. Frontend: a charting lib (candidate: Chart.js or ECharts — to be selected). Note: pick the library before building.

7. Recurring Transactions

  • Rules engine: scheduled, auto-repeating transactions (rent, salary) with a cadence (weekly/monthly/etc.) and optional end date.
  • Posting policy: per rule, either auto-post when due or prompt for confirmation on app open.
  • Manage view: create/pause/delete rules; generated transactions are tagged to their source rule.

Schema: new recurring_rules table (cadence, next_run, auto_post, end_date) + nullable transactions.recurring_rule_id. Backend: a startup scheduler that materialises due rules.

Cross-Cutting Tracks PLANNED

8. Backup & Restore

  • Export: one-click timestamped copy of the SQLite file to a chosen location.
  • Restore: load a backup file, with an integrity check before swapping it in.
  • Auto-backup before migrations — cheap insurance whenever user_version bumps.

Backend: export_backup, restore_backup file commands. No schema change.

9. Dark Mode / Theming

  • Light/dark toggle built on the existing CSS-variable palette (already tokenized in Tailwind config).
  • Respects system preference by default; user override persists.

Schema: a small app_settings key/value table (or local persistence) for the theme preference — reusable for future settings.

Deferred Backlog DEFERRED

Considered and intentionally not scheduled. Kept here because several are cheap to slot in later — the data model already accommodates some (profiles exist; accounts carry a currency).

FeatureWhy deferred / note
Reports & export (PDF/CSV)Lower priority than charts; revisit once analytics queries exist (they can feed exports).
Database encryption (SQLCipher)Stronger privacy, but adds build complexity (bundled SQLCipher) and a passphrase UX. Local file in a user-controlled folder is the current model.
Multi-profile switching UISchema (app_profiles) already supports it; just needs a switcher + profile-scoped queries. Easy to add when needed.
Multi-currency + conversionAccounts already store a currency; full cross-currency aggregation (rates, conversion) is significant scope.
Auto-update + signing/notarizationNeeded for real distribution, not for local development. Schedule before first public release.
Mobile (iOS/Android)Tauri v2 supports mobile, but the cloud-folder sync model gets trickier on mobile sandboxes. Large effort.
Localization (i18n)Multi-language UI + locale-aware number/date/currency formatting. Defer until the feature set stabilises.
Open question for charts: the charting library (Chart.js vs ECharts vs a Vue-native option) isn't chosen yet — worth deciding before Phase 3 work begins, as it affects bundle size and the dark-mode theming approach.
