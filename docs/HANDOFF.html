1 · What this is

Budetau is a local-first personal budget planner — a native macOS desktop app. All data lives in a single private SQLite file in the user's Documents folder (cloud-syncable). No servers, no accounts.

LayerTech
ShellTauri v2
FrontendVue 3 (<script setup>) + TypeScript + Vite + Pinia + Vue Router + Tailwind v3 + ApexCharts
BackendRust + rusqlite (bundled SQLite), serde
DBSQLite single file at ~/Documents/BudgetPlanner/budget.db; WAL disabled for cloud-sync safety

2 · Quick start

Toolchain is NOT on the default PATH. Node (Homebrew) and Rust (rustup) are installed but not on a non-login shell's PATH. Prefix every toolchain command with:
export PATH="$HOME/.cargo/bin:/opt/homebrew/bin:$PATH"
# run the desktop app (recompiles Rust + serves Vite)
npm run tauri dev

# frontend gate
npm run build        # vue-tsc --noEmit && vite build  (strict: noUnusedLocals/Parameters)
npm run lint         # eslint . --fix

# backend gate
cd src-tauri && cargo test          # 30 tests
cd src-tauri && cargo clippy -- -D warnings

Network/build commands need sandbox escape in this environment (dangerouslyDisableSandbox). The DB auto-creates and migrates on first launch.

3 · Data model

Money is always stored as INTEGER cents. Schema version tracked via PRAGMA user_version; migrations are append-only in src-tauri/src/db.rs (migrate_v1..v5), each bumping the version independently. v4 adds accounts.opening_balance (backfilled at migration time as balance − net transaction effect) so balances can be rebuilt from history without wiping the starting balance; it is kept internal to the DB layer (not on the Account IPC struct). v5 adds category_months for envelope budgeting (see §7 envelope epic) and backfills existing budgets.amount into the current month. v6 adds recurring_rules (scheduled transactions).

TableKey columns
app_profilesid, profile_name, created_at, db_sync_path
accountsid, profile_id, name, balance (cents), currency, type
categoriesid, profile_id, name, color_code, type, parent_id (v3: NULL = top-level; one level of nesting)
budgetsid, profile_id, category_id, period, amount (cents), alert_threshold (v2: 0–1 fraction) — legacy fixed-budget model; kept intact, superseded by envelopes
category_monthsid, profile_id, category_id, month ('YYYY-MM'), assigned (signed cents), UNIQUE(category_id, month) (v5: envelope budgeting)
recurring_rulesid, profile_id, account_id, amount, category_id, type, transfer_account_id, note, cadence (weekly/biweekly/monthly/yearly), next_due ('YYYY-MM-DD'), active (v6: scheduled transactions)
transactionsid, account_id, amount (cents, positive), category_id, date, note, type, transfer_account_id

Migrations: v1 core tables · v2 budgets.alert_threshold · v3 categories.parent_id. On a fresh DB, seeding adds a "Personal" profile, default categories (incl. example subs under Dining Out), and a default "Cash" account. Seeding is per-entity idempotent, so legacy DBs backfill a default account but do not get example sub-categories (by design).

4 · Conventions & invariants MUST READ

① Transaction amounts are a POSITIVE magnitude. The sign comes from type (expense subtracts, income adds, transfer moves between accounts). Never store a signed amount. The backend (insert_transaction / update_transaction_logic / adjust_balances) defensively .abs()es it. A signed amount inverts the dashboard net and corrupts balances — this was a real bug (fixed in fe435cd).
② Balances are mutated incrementally, not recomputed. Insert/update/delete adjust accounts.balance atomically inside one rusqlite transaction. This is fast but fragile: a bad write can drift a balance. Safety net (shipped): the recompute_balances command (Settings → Maintenance) rebuilds every accounts.balance as opening_balance + net transaction effect. The starting balance is preserved via the accounts.opening_balance column (migration v4) — set equal to balance on account creation — since there is no separate user-editable "opening balance" field.
③ Prettier config is semi:false. NEVER write multi-statement inline template handlers like @click="a = 1; b = 2" — Prettier strips the semicolons and reformats into invalid code that breaks the Vue compiler. Always extract to a method and use @click="myMethod". This broke the build twice.
④ Budgets roll up. A budget attaches to a top-level category; spending in any of its sub-categories counts toward it. The frontend uses categoryStore.descendantIds(id) for this. Category helpers live in src/stores/category.ts: topLevel, childrenOf, descendantIds, parentOf, displayPath (→ "Dining Out › Coffee").

IPC contract

  • Rust structs use #[serde(rename_all = "camelCase")]; frontend types in src/types/index.ts mirror them.
  • All 20 commands return Result<T, String>; typed wrappers in src/api.ts; Pinia stores own mutations and re-fetch affected stores (e.g. transaction mutations refresh accounts).
  • Commands: get_db_path, list/create/update/delete for accounts, categories, budgets, transactions (delete guards: account/category in use is refused), plus export_backup/restore_backup (file copy + integrity_check; restore auto-backs-up first, then re-runs init+seed_defaults to migrate an older backup forward) and recompute_balances (rebuilds balances from history; returns the refreshed accounts).

5 · How to verify UI changes

The app needs the Tauri runtime for real IPC, but you can drive the Vite dev server in a headless browser and mock window.__TAURI_INTERNALS__.invoke to render any data state. Pattern used throughout this project (preview tools):

// .claude/launch.json runs vite directly (node path, since npm isn't on PATH):
{ "name":"vite-dev","runtimeExecutable":"/opt/homebrew/bin/node",
  "runtimeArgs":["node_modules/vite/bin/vite.js","--port","1420"],"port":1420 }

// then in the page: define window.__TAURI_INTERNALS__.invoke = (cmd,args)=>Promise.resolve(mockData[cmd])
// navigate (click sidebar <a>) to remount views → they re-fetch with the mock.

ApexCharts has an entrance animation — screenshot after ~700ms. Always run the production build + lint after any lint --fix (Prettier can re-break inline handlers).

7 · Envelope-budgeting epic — SHIPPED (v1)

Zero-based envelope budgeting (Ready to Assign → Assigned → Activity → Available, with monthly rollover and move-money) replaces the legacy fixed-amount budgets model. All nine tasks (T1–T9) landed and are green. v1 scope: all accounts on-budget; income = inflow to Ready to Assign; credit-card categories & off-budget accounts deferred to v2.

SurfaceWhere
Schema (v5)category_months (signed assigned, per category/month); backfills legacy budgets.amount into the current month.
Enginecommands.rs: get_budget_month(month) → per-expense-category {assigned, activity, available} + readyToAssign; set_assigned(categoryId, month, amount) (absolute upsert).
Store/IPCbudgetMonth store; getBudgetMonth/setAssigned in api.ts; BudgetMonth/BudgetMonthCategory types.
Plan view/plan → PlanView.vue + plan/EnvelopeRow.vue + plan/MoveMoneyModal.vue: sticky RTA header, parent→sub table, inline-edit Assigned, month nav, move-money.
Income UXQuickAddModal.vue: income hides the category picker, shows "Ready to Assign", and posts categoryId=null. TransactionCard.vue labels such rows "Ready to Assign".
DashboardDashboardView.vue + dashboard/ReadyToAssignTile, EnvelopeSummaryStats, OverspentEnvelopes — reads its viewed month via a local getBudgetMonth fetch (not the shared store).
How it works — invariants to preserve when extending it:
  • Envelope assigned/activity/available are signed cents. The positive-cents invariant is transaction amounts only.
  • set_assigned is an absolute upsert (sets the value, not a delta). Inline-edit passes the new total; move-money reads each envelope's current assigned and sets from−X / to+X, so Ready to Assign is unchanged.
  • available = cumulative Σ(assigned + activity) for all months ≤ the target month (this is the rollover). readyToAssign = income(≤month) + Σ opening_balance − assigned(≤month, all categories) − uncategorized outflow(≤month). Transfers net to zero. Income must post with categoryId=null or it double-counts (RTA + envelope activity).
  • The engine returns a flat per-category read model; the Plan view does parent→sub grouping via categoryStore.
  • The Dashboard must not call budgetMonthStore.setMonth — that store is shared with the Plan screen; it fetches its own month into a local ref.
v2 refinements / deferred (not yet built):
  • Credit-card categories (a payment envelope that fills as you spend on the card) and off-budget accounts.
  • Cash overspend → next month: a negative available currently just rolls forward in that envelope; YNAB instead pulls cash overspending out of next month's Ready to Assign. Decide and implement.
  • Parent-envelope semantics — RESOLVED. A parent with sub-categories is now a read-only group header (Assigned/Activity/Available all show the rolled-up total, including the parent's own from the v5 backfill); only leaf categories are editable. See PlanView.vue hasChildren() + EnvelopeRow.vue's readonly prop. A parent's own assigned (if any) can still be moved out via the row's move-money button.
  • Dead legacy budget UI: budgets table + its CRUD commands and the now-unreferenced dashboard/BudgetCard.vue, AlertBanner.vue, AddBudgetModal.vue, ManageBudgetsModal.vue + the budget store remain in the tree (kept intact this epic). Remove once nothing depends on them.

Recommended workflow (what worked here)

  1. Wave 0 (you/orchestrator): do all schema migration + Rust commands + api.ts/types/store changes in the shared files yourself, commit as a checkpoint. This avoids parallel agents colliding on db.rs/commands.rs/lib.rs.
  2. Wave 1 (parallel agents): one agent per UI surface, each owning a disjoint set of files (a view + its components). Give each agent: the toolchain PATH rule, the Prettier-handler rule, the store helpers it needs, and "no public interface changes."
  3. Wave 2 (you): run the full gate on the merged tree, fix leftovers, visual-verify with the mock-invoke pattern, commit.

8 · Known issues / gotchas

  • Balance drift (invariant ②) — mitigated by the recompute_balances maintenance command (Settings → Maintenance). It is manual, not automatic; a bad write still drifts until the user runs it.
  • ApexCharts bundle ~518 kB → one chunk-size build warning. Harmless for desktop; lazy-load the Analytics route to silence it.
  • "Current month" captured at mount in Dashboard/Analytics — won't auto-advance past midnight if left open. Pre-existing, minor.
  • Stray git worktree: an agent left one under .claude/worktrees/ (gitignored). eslint now ignores .claude/**; remove with git worktree remove if it bothers you.
  • Example sub-categories only seed on a brand-new DB; existing DBs get the parent_id column but no example data (create subs in Settings → Categories).
