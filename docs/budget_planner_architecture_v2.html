Personal Budget Planner - Architecture & UI Specification

This document outlines the core architecture, data models, and implementation phases for the local-first personal budget planner application. The architecture prioritizes privacy and offline availability using Tauri and SQLite.

⚠ Original specification — partly superseded. This was the starting brief. The implementation has since evolved (Tauri v2, integer-cents money, schema migrations, one level of sub-categories, budgets, analytics). For the current architecture, conventions, and how to continue, read HANDOFF.html. The data model below has been updated to match what's actually built.

Technology Stack (Local-First Pivot)

Component Technology Purpose
Application Shell Tauri Packages the web frontend into a lightweight, native desktop executable.
Frontend Vue 3, TypeScript Provides a reactive user interface and client-side data formatting.
Backend Logic Rust Handles local file system operations, database connections, and system-level APIs.
Database SQLite A serverless, single-file database optimized for local storage and cloud-folder syncing.

Data Models & Categorization

Updated to the shipped schema. Categories support one level of nesting (a parent_id, NULL = top-level) — the original "flat tags" decision was revised so spend can be detailed (e.g. Dining Out → Coffee) while still rolling up to the parent's budget. All money is stored as INTEGER cents. Schema version is tracked via PRAGMA user_version (currently v3).
Entity Fields Description
AppProfile id, profile_name, created_at, db_sync_path Local user profiles (e.g., "Personal", "Business").
Account id, profile_id, name, balance (cents), currency, type Bank accounts, credit cards, or cash wallets. Balance is maintained atomically by transaction mutations.
Category id, profile_id, name, color_code, type, parent_id Budget categories. parent_id gives one level of sub-categories (v3).
Budget id, profile_id, category_id, period, amount (cents), alert_threshold Per-category monthly limit; alert_threshold (0–1, v2) is the % at which it's "near". Attaches to top-level categories; sub-spend rolls up.
Transaction id, account_id, amount (positive cents), category_id, date, note, type, transfer_account_id Income / expense / transfer. amount is a positive magnitude; the sign comes from type. transfer_account_id is the destination for transfers.

UI Architecture & Frontend Goals

Dashboard Layout

  • Hero Section: High-level summary displaying Total Spend vs. Total Income for the current month.
  • Attention Banners: Conditional alert components that trigger when specific categories are near or over their limits (e.g., "Warning: Dining Out is at 95% of budget").
  • Budget Cards: A responsive grid of cards for each active category, displaying visual progress bars (spent vs. remaining).

Transaction Entry (Rapid Modal)

  • Trigger: Accessible via a floating action button (FAB) or a global keyboard shortcut (e.g., Cmd+K).
  • Default View: Streamlined to just three inputs: Amount, Category (with autocomplete), and Date (defaults to today).
  • Expansion: An "Add Details" toggle to reveal optional fields like Notes or specific Account selectors.

Data Display Density

  • Card-Based UI: Standard transactions will be displayed using a TransactionCard.vue component showing the Category icon/color, Amount, and Date, rather than dense spreadsheet grids, ensuring a clean and modern aesthetic.

Phase 1: Local Infrastructure Setup (Agent Delegation Plan)

Phase 1 has been heavily detailed and divided into modular sub-tasks designed to be delegated to AI agents or developers. Strict dependencies must be followed to avoid blocking.

Task 1A: Core Project Scaffolding

  • Status: PREREQUISITE FOR ALL OTHER TASKS.
  • Instructions for Agent:
    1. Initialize the Tauri workspace using the npm create tauri-app@latest utility. Select Vue, TypeScript, and Vite.
    2. Configure tsconfig.json with strict type checking enabled to ensure robust component development.
    3. Set up ESLint and Prettier for the Vue frontend to maintain standardized formatting.
    4. Configure src-tauri/Cargo.toml with serde, serde_json, and tauri core dependencies. Add clippy and rustfmt to the environment requirements.
    5. Verify the application builds successfully and runs the dev server via npm run tauri dev.

Task 1B: SQLite Backend & Path Resolution

  • Dependencies: Requires Task 1A.
  • Execution Status: Can run in PARALLEL with Task 1C.
  • Instructions for Agent:
    1. Add the rusqlite (with the bundled feature) and serde_rusqlite crates to the Tauri backend.
    2. Implement a Rust module using tauri::api::path::document_dir to dynamically resolve the database storage path. The fallback should be a local app data folder if a cloud-sync folder (like iCloud) is unavailable.
    3. Write a db::init() function to execute the CREATE TABLE IF NOT EXISTS strings for AppProfile, Account, Transaction, and Category.
    4. Crucial: Explicitly execute PRAGMA journal_mode = DELETE; or TRUNCATE; upon connection initialization to disable WAL (Write-Ahead Logging). This prevents the creation of -wal and -shm files that severely conflict with cloud sync engines.
    5. Implement a thread-safe SQLite connection manager using std::sync::Mutex wrapped in Tauri's managed state so commands can safely access the database.

Task 1C: Frontend Foundation & State Management

  • Dependencies: Requires Task 1A.
  • Execution Status: Can run in PARALLEL with Task 1B.
  • Instructions for Agent:
    1. Clean out the boilerplate Vite/Vue code. Set up standard directories: src/components, src/views, src/stores, src/types.
    2. Install and configure Pinia. Create useTransactionStore and useAccountStore with structured state representations (e.g., data, isLoading, error).
    3. Install and configure Vue Router. Define the base paths: /dashboard (default routing), /transactions, and /settings.
    4. Install Tailwind CSS via PostCSS. Configure tailwind.config.js to scan Vue components and set up a custom color palette matching the UI architecture specification.
    5. Build a persistent responsive layout (App.vue) with a fixed navigation sidebar and a main scrollable content area.

Task 1D: The IPC (Inter-Process Communication) Bridge

  • Dependencies: Requires BOTH Task 1B and Task 1C to be completed.
  • Instructions for Agent:
    1. In the Rust backend, define Tauri commands with the #[tauri::command] macro for standard CRUD operations. Ensure these functions return Result<T, String> to smoothly map Rust errors to frontend rejections.
    2. In src/types/index.ts, define frontend TypeScript interfaces that strictly map to the Rust struct properties (handling camelCase to snake_case conversions where necessary).
    3. Create a frontend api.ts utility file wrapping @tauri-apps/api/invoke. Provide strongly-typed async functions (e.g., export const fetchAccounts = (): Promise<Account[]> => invoke('get_accounts')).
    4. Wire the Pinia stores to these api.ts actions so the UI reactively updates state when transactions are added or account balances change.
    5. Implement the "Settings" view to invoke a get_db_path Rust command, displaying the active SQLite file location so the user can verify their local-first sync setup.
