Personal Budget Planner — Phase 1 Build Plan

✅ Delivered — historical plan. Phase 1 (local infrastructure) shipped and the app has since grown well beyond it (Phases 2–3 + sub-categories). Kept for provenance. Current reference: HANDOFF.html.

Context

The repository currently contains only the specification document (budget_planner_architecture_v2.html) and no code. This plan stands up Phase 1: Local Infrastructure for a local-first, privacy-focused budget planner — a Tauri desktop app with a Vue 3 + TypeScript frontend and an embedded SQLite database stored in a single, cloud-syncable file.

Before delegating to agents, the spec was pressure-tested and four issues were corrected. The decisions below (confirmed with the user) override the spec where they conflict.

#DecisionWhy
1Target Tauri v2The spec's tauri::api::path::document_dir and @tauri-apps/api/invoke are Tauri v1 and will not compile against the v2 scaffold produced by create tauri-app@latest.
2Money as integer minor unitsStore cents in INTEGER columns, format in Vue. Floats lose precision — unacceptable for money.
3Add a Budget entityThe dashboard's limit banners ("95% of budget") and progress bars had no backing data model.
4Sequential → parallel → bridgeOne agent scaffolds (1A), two run in parallel (1B backend / 1C frontend), one wires the IPC bridge (1D).
Prerequisite blocker: Node.js + npm and the Rust toolchain (cargo/rustc) are not installed on this machine. Homebrew and Xcode Command Line Tools are present. Node (via Homebrew) and Rust (via rustup) must be installed before any agent can build.

Corrected Data Model

All money fields are INTEGER minor units (cents). Enable PRAGMA foreign_keys = ON and track schema version via PRAGMA user_version.
EntityFieldsNotes
AppProfileid, profile_name, created_at, db_sync_pathLocal profiles.
Accountid, profile_id, name, balance (INTEGER cents), currency, typeBalance is maintained atomically, not a float.
Categoryid, profile_id, name, color_code, typeFlat tag structure.
Budgetid, profile_id, category_id, period (e.g. 'monthly'), amount (INTEGER cents)NEW — powers limit banners & progress bars.
Transactionid, account_id, amount (INTEGER cents), category_id, date, note, type, transfer_account_id (nullable)transfer_account_id added so type='transfer' can express from → to.
  • Rust structs use #[serde(rename_all = "camelCase")] so the frontend receives camelCase without manual mapping.
  • On connection init: PRAGMA journal_mode = DELETE; (avoids -wal/-shm files fighting cloud sync), PRAGMA foreign_keys = ON;, and a user_version-gated migration runner.

Tauri v2 API Corrections (apply throughout)

  • Path resolution: app.path().document_dir() via tauri::Manager — not tauri::api::path::document_dir.
  • Frontend invoke: import { invoke } from '@tauri-apps/api/core' — not @tauri-apps/api.
  • Capabilities: declare permissions in src-tauri/capabilities/*.json for any FS access.
  • SQLite: rusqlite (feature bundled) compiled into the Rust backend, exposed via #[tauri::command]s (not the JS sql plugin).

Execution Plan (Agent Delegation)

1A Scaffold → 1B Backend1C Frontend → 1D IPC Bridge

Task 1A — Scaffold BLOCKS ALL

  • npm create tauri-app@latest → Vue + TypeScript + Vite, Tauri v2.
  • Strict tsconfig.json; ESLint + Prettier; clippy + rustfmt.
  • src-tauri/Cargo.toml: tauri v2, serde, serde_json.
  • Verify npm run tauri dev builds and runs. Commit before parallel work begins.

Task 1B — SQLite Backend PARALLEL w/ 1C

Directory: src-tauri/

  • Add rusqlite (bundled) + serde_rusqlite.
  • Path resolver: document_dir() first, fallback to app-data dir.
  • db::init(): the PRAGMAs above + CREATE TABLE IF NOT EXISTS for all 5 entities incl. Budget; seed default categories on first run.
  • Thread-safe Mutex<Connection> in Tauri managed state.
  • Rust unit tests for db::init() and path resolution.

Task 1C — Frontend Foundation PARALLEL w/ 1B

Directory: src/

  • Clean boilerplate; dirs components/ views/ stores/ types/.
  • Pinia: useTransactionStore, useAccountStore, useBudgetStore (data/isLoading/error).
  • Vue Router: /dashboard (default), /transactions, /settings.
  • Tailwind via PostCSS, custom palette from the spec.
  • Responsive App.vue shell: fixed sidebar + scrollable main.

Task 1D — IPC Bridge NEEDS 1B + 1C

  • #[tauri::command] CRUD returning Result<T, String>; atomic balance update inside the same DB transaction as the transaction insert (pulled forward from Phase 2 to prevent balance drift).
  • src/types/index.ts interfaces mirroring Rust structs (camelCase via serde rename).
  • src/api.ts wrapping invoke with typed async functions (e.g. fetchAccounts(): Promise<Account[]>).
  • Wire Pinia stores → api.ts actions.
  • Settings view invokes get_db_path to display the active SQLite file location.

Out of Scope (Later Phases)

  • Dashboard hero / banners / cards rendering — Phase 1 builds the data + shell only.
  • CSV bank-statement import (Phase 3).
  • Charts / historical cash-flow trends (Phase 3).

Verification

  • After 1A: npm run tauri dev opens a window; cargo clippy and ESLint pass clean.
  • After 1B: cargo test passes; launching the app creates the SQLite file in the document dir with all 5 tables and no -wal/-shm files; user_version set.
  • After 1C: npm run dev renders the sidebar shell; routes navigate; Pinia devtools show the three stores.
  • After 1D (end-to-end): Settings view displays the DB path; adding a transaction updates the account balance atomically and the Pinia store reactively reflects it; round-trip a record (insert → fetch → assert) confirms snake_case ↔ camelCase mapping.
  • Final gate: cargo test + cargo clippy clean, frontend typechecks (vue-tsc --noEmit), app boots and persists data across restarts.
